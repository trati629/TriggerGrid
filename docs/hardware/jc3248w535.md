# Guition JC3248W535 — Board Specification, LVGL Integration & Troubleshooting

Board: **Guition JC3248W535**
SoC: **ESP32-S3** (dual-core 240 MHz, 8 MB PSRAM, 16 MB Flash)
Display: **3.2″ IPS** via QSPI (AXS15231B driver IC, physical panel 320×480 portrait-native)
Touch: **Capacitive** via I2C (AXS15231B — same chip, dual-function)
USB: **USB-C** (CDC on boot)

> **Physical orientation**: The device enclosure is landscape (shorter side up). The panel itself is wired
> portrait-native (320 columns × 480 rows). All landscape rendering requires either software rotation or
> a canvas wrapper — hardware MADCTL rotation is unreliable on this chip variant (see §Problems).

---

## Platform & Framework

**Required platform:** pioarduino (Arduino core 3.x)

The GFX Library for Arduino ≥ 1.6.0 depends on `esp_lcd_panel_ops.h` / `esp32-hal-periman.h`, which only
exist in Arduino core 3.x. The default `espressif32` platform ships core 2.x and will not compile.

```ini
platform = https://github.com/pioarduino/platform-espressif32/releases/download/53.03.13/platform-espressif32.zip
```

Any `53.x.x` pioarduino release works. Do not use `espressif32` from the default registry for this board.

## platformio.ini (working baseline)

```ini
[env:guition-jc3248w535]
platform = https://github.com/pioarduino/platform-espressif32/releases/download/53.03.13/platform-espressif32.zip
board = esp32-s3-devkitc-1
framework = arduino
monitor_speed = 115200
board_build.arduino.memory_type = qio_opi
board_build.flash_mode = dio
board_build.filesystem = littlefs
board_build.partitions = default_16MB.csv
board_upload.flash_size = 16MB
board_build.f_cpu = 240000000L
build_flags =
    -DCORE_DEBUG_LEVEL=0
    -DBOARD_HAS_PSRAM
    -DARDUINO_USB_CDC_ON_BOOT=1
lib_deps =
    moononournation/GFX Library for Arduino @ ^1.6.0
    lvgl/lvgl @ ^9.0.0
```

This is the minimal baseline for the board. The project's own `platformio.ini` adds the LVGL config
flags and the other libraries, and pins LVGL more tightly.

Key flags:
- `qio_opi` — required for PSRAM (OPI PSRAM on this board)
- `dio` flash mode — works reliably; `qio` can cause boot failures on some units
- `default_16MB.csv` — 16 MB flash partition table
- `board_upload.flash_size = 16MB` — `esp32-s3-devkitc-1` assumes 8 MB. Without this the image header
  says 8 MB, `ESP.getFlashChipSize()` reports 8192 KB, and partitions past 8 MB can be rejected at boot
- `BOARD_HAS_PSRAM` — enables PSRAM in the Arduino core; without this `ps_malloc` returns null

## Display Initialisation (Arduino_GFX)

```cpp
#include <Arduino_GFX_Library.h>

Arduino_DataBus *bus = new Arduino_ESP32QSPI(
    45,  // CS
    47,  // SCK
    21,  // D0
    48,  // D1
    40,  // D2
    39   // D3
);

// RST=GFX_NOT_DEFINED — RST pin is wired but passing it to the constructor
// breaks init on some units. Drive RST manually or omit entirely.
Arduino_GFX *gfx = new Arduino_AXS15231B(
    bus,
    GFX_NOT_DEFINED,   // RST — omit; passing GPIO 38 can break init
    0,                 // rotation — keep 0; MADCTL rotation is broken (see §Problems)
    false,             // ips — false with type1 init ops; true with default ops
    320,               // width  (portrait-native panel)
    480,               // height (portrait-native panel)
    0, 0, 0, 0,
    axs15231b_320480_type1_init_operations,       // ← CRITICAL: must not use default
    sizeof(axs15231b_320480_type1_init_operations)
);

void setup() {
    gfx->begin();
    gfx->fillScreen(BLACK);
}
```

### Init sequence — the most critical configuration on this board

`Arduino_AXS15231B` ships with **three** init sequences:

| Constant                                  | Panel size | Notes                                    |
|-------------------------------------------|------------|------------------------------------------|
| `axs15231b_180640_init_operations`        | 180×640    | **Default** — wrong for JC3248W535       |
| `axs15231b_320480_type1_init_operations`  | 320×480    | **Correct for JC3248W535** — use this    |
| `axs15231b_320480_type2_init_operations`  | 320×480    | Alternative; not tested on this board    |

Passing the wrong init sequence causes the panel to show nothing (or only a single dashed line).
Always pass `axs15231b_320480_type1_init_operations` and its `sizeof()` explicitly — do not rely on the
default constructor.

## Touch Read Protocol (AXS15231B)

The AXS15231B requires an 8-byte unlock command written via I2C **before every read**. Without it,
all bytes come back zero. There is no publicly documented register map; this was reverse-engineered
from the ESPHome driver source.

```cpp
#define TOUCH_ADDR 0x3B

void touchReadNow() {
    // 1. Write unlock command — FULL STOP (no repeated-start)
    static const uint8_t CMD[8] = {
        0xb5, 0xab, 0xa5, 0x5a, 0x00, 0x00, 0x00, 0x08
    };
    Wire.beginTransmission(TOUCH_ADDR);
    Wire.write(CMD, 8);
    Wire.endTransmission();   // STOP — do NOT use endTransmission(false)

    // 2. Read 8 bytes
    uint8_t data[8] = {};
    Wire.requestFrom((uint8_t)TOUCH_ADDR, (uint8_t)8);
    for (uint8_t i = 0; i < 8; i++) data[i] = Wire.read();

    // 3. Decode — portrait coords (x: 0–319, y: 0–479)
    if (data[0] == 0 && data[1] > 0) {
        int x = ((data[2] & 0x0F) << 8) | data[3];
        int y = ((data[4] & 0x0F) << 8) | data[5];
    }
}
```

**Gotcha — repeated-start:** `endTransmission(false)` causes the chip to ignore the command and
return zeros. Always full STOP.

**Gotcha — INT timing:** The chip fires 3–6 FALLING pulses per touch within ~200 ms. Data is only
valid for <1 ms after each INT; read immediately in the ISR or via a flag.

**Gotcha — release detection:** There is no "finger up" interrupt. Declare release if no INT arrives
within ~80 ms of the last pulse.

## LVGL 9.x Integration (working portrait baseline)

The following produces a clean, artifact-free portrait (320×480) rendering. It is the confirmed
working baseline. Landscape requires additional steps — see §Landscape Orientation below.

### lv_conf.h essentials

```c
#define LV_COLOR_FORMAT_DEFAULT LV_COLOR_FORMAT_RGB565   // 16-bit panel
#define LV_FONT_MONTSERRAT_24 1    // enable fonts you use
```

On LVGL ≥ 9.5, use `LV_COLOR_FORMAT_DEFAULT`. The older `LV_COLOR_DEPTH 16` still works but prints a
deprecation warning in every LVGL file. Ticks are driven manually with `lv_tick_inc()` (§P8).

Wrap the entire file in `#ifndef __ASSEMBLER__` / `#endif` to prevent preprocessor errors
when PlatformIO assembles startup stubs.

### Draw buffer — PSRAM allocation

```cpp
const size_t BUF_PIXELS = (size_t)DISP_W * (size_t)DISP_H;   // 320×480
uint16_t* draw_buf = (uint16_t*)ps_malloc(BUF_PIXELS * sizeof(uint16_t));
if (!draw_buf) { /* fatal */ }
memset(draw_buf, 0, BUF_PIXELS * sizeof(uint16_t));  // ps_malloc does NOT zero memory
```

`ps_malloc` allocates in PSRAM but does not zero the region. Without `memset`, stale PSRAM data
from a previous boot appears as garbage pixels wherever LVGL hasn't yet rendered.

### Display registration

```cpp
lv_display_t* disp = lv_display_create(DISP_W, DISP_H);       // 320, 480
lv_display_set_color_format(disp, LV_COLOR_FORMAT_RGB565);
lv_display_set_buffers(disp, draw_buf, nullptr,
                        (uint32_t)(BUF_PIXELS * sizeof(uint16_t)),
                        LV_DISPLAY_RENDER_MODE_FULL);
lv_display_set_flush_cb(disp, flush_cb);
lv_display_set_rotation(disp, LV_DISPLAY_ROTATION_0);
```

### Flush callback

```cpp
static void flush_cb(lv_display_t* disp, const lv_area_t* area, uint8_t* px_map) {
    Arduino_GFX* gfx = display_get_gfx();
    // Use gfx->width()/height() directly — NOT area coords.
    // With any lv_display_set_rotation(), area coords are in logical (rotated) space
    // but the physical buffer is always portrait; mixing them causes stripe artifacts.
    gfx->draw16bitRGBBitmap(0, 0, (uint16_t*)px_map,
                             (int16_t)gfx->width(), (int16_t)gfx->height());
    lv_display_flush_ready(disp);
}
```

### Tick driver

```cpp
// In loop() — advance LVGL clock manually
static uint32_t last_ms = 0;
uint32_t now = millis();
lv_tick_inc(now - last_ms);
last_ms = now;
lv_timer_handler();
```

LVGL's own tick mechanism (`LV_TICK_CUSTOM`) may not activate when LVGL compiles as a separate
PlatformIO library unit (its `.c` files don't see your `lv_conf.h` in `include/`). Driving ticks
manually is reliable regardless.

## Landscape Orientation — Problem Analysis

The device enclosure places the display in landscape orientation (wider than tall: 480 wide × 320 tall).
The physical panel is portrait-native (320 wide × 480 tall). To render correctly in landscape, one
of the following coordinate-transformation approaches must be used.

### Why the obvious approaches don't work

| Approach | Result | Root cause |
|----------|--------|------------|
| `Arduino_AXS15231B(... rotation=1 ...)` | Blank / corrupted display | AXS15231B MADCTL implementation is incomplete on this chip variant; MADCTL updates only during V-sync in Sleep Out mode and the command is silently ignored or partially applied |
| `lv_display_set_rotation(LV_DISPLAY_ROTATION_90)` | Display output breaks entirely | LVGL remaps the render buffer stride for the rotated dimensions; the flush callback receives a 480×320 buffer but the physical display expects 320×480 — dimension inversion causes the controller to receive malformed data |
| `lv_display_set_rotation(LV_DISPLAY_ROTATION_270)` | Each row shifted; orientation still portrait | Even on LVGL 9.5.0 (stride bug reportedly fixed) the flush callback receives the buffer in logical (480-wide row) layout. Passing it with `gfx->width()=320` causes each landscape row to wrap into the next, producing the row-shift symptom. LVGL software rotation fills the buffer in logical space and expects the flush to handle physical mapping — which our GFX call did not. |

### Five candidate solutions

---

### Solution 1 — Arduino_Canvas rotation wrapper (recommended, no MADCTL, no LVGL rotation)

Wrap the physical AXS15231B display in an `Arduino_Canvas` configured at landscape dimensions.
The canvas holds a 480×320 framebuffer in PSRAM. When flushed, `Arduino_Canvas` handles the
coordinate mapping from canvas space to physical display space internally.

```cpp
// display.cpp — create physical display, then wrap it
Arduino_GFX* s_phys = new Arduino_AXS15231B(bus, GFX_NOT_DEFINED, 0, false,
                           320, 480, 0, 0, 0, 0,
                           axs15231b_320480_type1_init_operations,
                           sizeof(axs15231b_320480_type1_init_operations));

// Canvas at rotated (landscape) dimensions; rotation=1 tells the canvas
// how to map its pixels onto the physical display
Arduino_Canvas* s_gfx = new Arduino_Canvas(480, 320, s_phys, 0, 0, 1);
s_gfx->begin();
```

```cpp
// lvgl_glue.cpp — LVGL sees 480×320; flush pushes canvas to physical
// lv_display_create(480, 320)      ← landscape logical size
// lv_display_set_rotation(ROTATION_0)  ← no LVGL rotation needed
// draw_buf must be 480×320×2 bytes

static void flush_cb(lv_display_t*, const lv_area_t*, uint8_t* px_map) {
    Arduino_Canvas* canvas = (Arduino_Canvas*)display_get_gfx();
    // Copy LVGL's rendered frame into the canvas framebuffer
    memcpy(canvas->getFramebuffer(), px_map, 480 * 320 * sizeof(uint16_t));
    canvas->flush();   // canvas handles the physical rotation internally
    lv_display_flush_ready(disp);
}
```

**Pros:** No dependency on MADCTL; no LVGL stride bugs; Arduino_Canvas's rotation is battle-tested.
**Cons:** Extra memcpy (can be avoided by pointing LVGL's buffer directly at canvas framebuffer).
**Risk:** Canvas rotation=1 must produce the correct physical orientation for this panel; if it maps
to 180° instead of 90°, swap to rotation=3.

---

### Solution 2 — Manual pixel rotation in flush_cb using lv_draw_sw_rotate()

Keep the physical display as portrait (rotation=0, 320×480). Tell LVGL the logical display is
landscape (480×320, ROTATION_0). In the flush callback, software-rotate the entire 480×320 frame
into a second 320×480 buffer, then push that to the hardware.

```cpp
// Allocate two buffers: one for LVGL rendering (480×320), one for rotated output (320×480)
uint16_t* lvgl_buf  = (uint16_t*)ps_malloc(480 * 320 * 2);
uint16_t* phys_buf  = (uint16_t*)ps_malloc(320 * 480 * 2);
memset(lvgl_buf, 0, 480 * 320 * 2);
memset(phys_buf, 0, 320 * 480 * 2);

// LVGL display — logical landscape size, no software rotation
lv_display_t* disp = lv_display_create(480, 320);
lv_display_set_buffers(disp, lvgl_buf, nullptr, 480*320*2, LV_DISPLAY_RENDER_MODE_FULL);
lv_display_set_rotation(disp, LV_DISPLAY_ROTATION_0);

// Flush: rotate 90° CCW into phys_buf, then push to display
static void flush_cb(lv_display_t*, const lv_area_t*, uint8_t* px_map) {
    lv_draw_sw_rotate(px_map,    480, 320, 480 * 2,   // src: 480×320 landscape
                      phys_buf,  320 * 2,             // dst: 320×480 portrait
                      LV_DISPLAY_ROTATION_270,        // 270° CCW == 90° CW
                      LV_COLOR_FORMAT_RGB565);
    gfx->draw16bitRGBBitmap(0, 0, phys_buf, 320, 480);
    lv_display_flush_ready(disp);
}
```

**Pros:** No dependency on MADCTL; explicit and debuggable; no hidden canvas magic.
**Cons:** `lv_draw_sw_rotate()` iterates every pixel (~150K pixels at 2 bytes) — adds ~5–10 ms per
frame on ESP32-S3. Try `LV_DISPLAY_ROTATION_90` vs `_270` — LVGL 9.0.0 had them swapped (fixed in 9.0.1).
**Risk:** Rotation direction (90 vs 270) must be verified empirically.

---

### Solution 3 — LVGL software rotation with stride fix (ROTATION_270 + corrected flush)

The ROTATION_270 test showed the button rendering correctly but with stripe artifacts. Those artifacts
were caused by a stride mismatch in the flush callback (area coords used instead of gfx dimensions).
That bug is already fixed. Re-test ROTATION_270 with the current flush callback and a correctly
sized 480×320 draw buffer.

```cpp
// In this repo these are PANEL_W / PANEL_H in include/board_pins.h
static constexpr int16_t DISP_W = 320;   // physical portrait width
static constexpr int16_t DISP_H = 480;   // physical portrait height

// lvgl_glue.cpp — ROTATION_270 maps 320×480 physical → 480×320 logical
const size_t BUF_PIXELS = 320 * 480;       // physical size — buffer is always physical
uint16_t* draw_buf = (uint16_t*)ps_malloc(BUF_PIXELS * 2);
memset(draw_buf, 0, BUF_PIXELS * 2);

lv_display_t* disp = lv_display_create(320, 480);   // PHYSICAL size
lv_display_set_rotation(disp, LV_DISPLAY_ROTATION_270);
// After setting rotation, LVGL exposes the logical display as 480×320

// Flush callback (already correct in current codebase):
static void flush_cb(lv_display_t*, const lv_area_t*, uint8_t* px_map) {
    gfx->draw16bitRGBBitmap(0, 0, (uint16_t*)px_map,
                             (int16_t)gfx->width(), (int16_t)gfx->height());
    lv_display_flush_ready(disp);
}
```

**Pros:** Uses LVGL's built-in rotation machinery; minimal code change.
**Cons:** LVGL 9.2 stride bug may still affect partial-frame renders; artifacts may reappear with
complex UIs. Also: ROTATION_270 renders the correct orientation on screen but content appears
90° off (still investigable). Swap to ROTATION_90 if 270 produces wrong orientation.
**Risk:** Depends on whether the LVGL version in use has the stride recalculation fix applied
(`layer->draw_buf->header.stride` must update after rotation).

### Solution 4 — Logical landscape display dimensions with software transpose in flush_cb ✅ CONFIRMED WORKING

Tell LVGL the display is 480×320 at ROTATION_0. The physical AXS15231B is still portrait (320×480).
`flush_cb` receives the 480×320 LVGL buffer and software-transposes it into a 320×480 physical buffer
before pushing to hardware. The touch driver must map the chip's portrait coordinates to landscape
in the same direction: `lx = py`, `ly = 319 − px` (done in `src/touch/`, milestone M3).

This is the approach used by several JC3248W535 community builds and is the **confirmed working
solution** for this project (verified 2026-06-01).

```cpp
// In this repo: PANEL_W/PANEL_H and SCREEN_W/SCREEN_H in include/board_pins.h
static constexpr int16_t DISP_W = 320;   // physical portrait width
static constexpr int16_t DISP_H = 480;   // physical portrait height
static constexpr int16_t LAND_W = 480;   // logical landscape width  (LVGL / touch)
static constexpr int16_t LAND_H = 320;   // logical landscape height (LVGL / touch)

// lvgl_glue.cpp — two PSRAM buffers, each 480×320×2 = 307 200 bytes
uint16_t* s_draw_buf = (uint16_t*)ps_malloc(LAND_W * LAND_H * 2);  // LVGL renders here
uint16_t* s_phys_buf = (uint16_t*)ps_malloc(LAND_W * LAND_H * 2);  // transpose output

// LVGL: 480×320 landscape, no software rotation
lv_display_t* disp = lv_display_create(LAND_W, LAND_H);
lv_display_set_rotation(disp, LV_DISPLAY_ROTATION_0);
lv_display_set_buffers(disp, s_draw_buf, nullptr, LAND_W*LAND_H*2, LV_DISPLAY_RENDER_MODE_FULL);
lv_display_set_flush_cb(disp, flush_cb);

// Flush: 90° CCW transpose (matches the touch mapping lx=py, ly=319-px)
static void flush_cb(lv_display_t* disp, const lv_area_t*, uint8_t* px_map) {
    const uint16_t* src = (const uint16_t*)px_map;
    uint16_t*       dst = s_phys_buf;
    for (int row = 0; row < LAND_H; row++) {
        for (int col = 0; col < LAND_W; col++) {
            dst[col * LAND_H + (LAND_H - 1 - row)] = src[row * LAND_W + col];
        }
    }
    gfx->draw16bitRGBBitmap(0, 0, s_phys_buf, DISP_W, DISP_H);
    lv_display_flush_ready(disp);
}
// Touch: map portrait IC coords → landscape (lx = py, ly = 319 - px) in the touch driver.
```

**Pros:** Completely bypasses MADCTL and LVGL rotation; pure software, debuggable, no library surprises.
**Cons:** Two full-frame PSRAM allocations (614 KB total); nested transpose loop ~5–10 ms/frame.
**Note:** The 90° CCW formula `dst[col * LAND_H + (LAND_H-1 - row)]` matches the touch decode
direction. For 90° CW instead, use `dst[(DISP_H-1 - col) * DISP_W + row]`.

### Solution 5 — IPS flag investigation + type2 init sequence

Before assuming MADCTL is permanently broken, verify whether `ips=true` combined with
`axs15231b_320480_type2_init_operations` enables working MADCTL rotation. Some AXS15231B
production variants respond to MADCTL only when the IPS inversion flag is set in the init sequence.

```cpp
// Test configuration A — type2 init with ips=true
Arduino_AXS15231B(bus, GFX_NOT_DEFINED, 1 /* rotation */, true /* ips */,
                   320, 480, 0, 0, 0, 0,
                   axs15231b_320480_type2_init_operations,
                   sizeof(axs15231b_320480_type2_init_operations));

// Test configuration B — type1 init with ips=true + rotation=1
Arduino_AXS15231B(bus, GFX_NOT_DEFINED, 1, true, 320, 480, 0, 0, 0, 0,
                   axs15231b_320480_type1_init_operations,
                   sizeof(axs15231b_320480_type1_init_operations));
```

If either produces a working landscape image: hardware MADCTL works on this unit, and the earlier
rotation=1 failure was due to the ips flag mismatch inverting the panel voltage rail at the wrong
moment in the init sequence.

**Pros:** If it works, it's the simplest and fastest approach (hardware rotation, zero CPU overhead).
**Cons:** May still produce a blank screen; init sequence interaction with MADCTL is undocumented.
**Risk:** May break display entirely as before. Flash revert is fast.

## Problems Encountered & Resolutions

### P1 — Blank screen at boot (no test pattern)

**Symptom:** Display shows nothing after boot — sometimes a single dashed line, sometimes solid white.

**Root cause:** `Arduino_AXS15231B` default constructor uses `axs15231b_180640_init_operations`
(designed for a 180×640 panel). This init sequence sends the wrong COLMOD / RASET / CASET values
for the 320×480 panel in the JC3248W535. The panel powers up but the display controller is
misconfigured and shows no output.

**Fix:** Always pass `axs15231b_320480_type1_init_operations` and `sizeof(...)` explicitly as the
last two arguments to the `Arduino_AXS15231B` constructor. Do not rely on the default.

---

### P2 — MADCTL hardware rotation (rotation=1) breaks display entirely

**Symptom:** Changing `Arduino_AXS15231B` constructor to `rotation=1` produced a blank or corrupted
display. Neither the test pattern nor the LVGL button rendered. The display was stuck in a bad state
until reflashed with rotation=0.

**Root cause:** The AXS15231B chip variant used in the JC3248W535 has an incomplete or broken MADCTL
implementation. According to the AXS15231B datasheet and reports from esp-iot-solution issue #579,
MADCTL (0x36 command) updates are only processed during V-sync in Sleep Out mode; on this variant
the command appears to be silently ignored or partially applied, leaving the panel in an undefined
state. Setting `ips=false` with rotation=1 additionally risks sending the wrong inversion polarity
before the panel is ready.

**Fix:** Keep `rotation=0` always. Use software rotation (see §Landscape Orientation).

---

### P3 — LVGL ROTATION_90 breaks display output entirely

**Symptom:** Changing to `lv_display_set_rotation(LV_DISPLAY_ROTATION_90)` caused the display to
show corrupted output or nothing. Reverting to ROTATION_0 restored correct output.

**Root cause:** LVGL ROTATION_90 changes the logical display dimensions from 320×480 to 480×320.
The flush callback then calls `gfx->draw16bitRGBBitmap(0, 0, buf, gfx->width(), gfx->height())`.
`gfx->width()` still returns 320 (physical) but the buffer now contains 480 columns. The hardware
receives a frame with incorrect stride, producing corrupted output. The AXS15231B may also enter
a bad state when it receives more data bytes than expected for its RASET/CASET window.

**Fix:** Reverted to ROTATION_0. If ROTATION_90 is re-attempted, the flush callback must know
the buffer dimensions are now swapped and pass 480, 320 to `draw16bitRGBBitmap`.

---

### P4 — LVGL ROTATION_270 shows stripe artifacts across background

**Symptom:** With ROTATION_270, the LVGL button was visible and positioned correctly but a grid of
fine stripes appeared over the background. The button itself appeared on the correct half of the
screen but at 90° off.

**Root cause (stripes):** The flush callback was using `area->x2 - area->x1 + 1` and
`area->y2 - area->y1 + 1` as width/height for `draw16bitRGBBitmap`. With LVGL software rotation,
the `area` parameter is in **logical** (rotated) space, not physical space. The physical buffer
is still portrait (320×480) but the area coords described a landscape region, causing the bitmap
call to read the wrong number of columns per row — producing regular stripes.

**Root cause (orientation):** Button visible but rotated 90° = LVGL is rotating the coordinate
system but the physical buffer/flush still don't align. Needs the full landscape solution (one
of the five approaches above).

**Fix (stripes):** Changed flush callback to use `gfx->width()` and `gfx->height()` directly instead
of computing from area coords. This fixed the stripes but did not fix orientation.

---

### P5 — Stale PSRAM garbage in framebuffer

**Symptom:** On first render after boot, regions of the screen that LVGL had not yet drawn showed
random pixel patterns — multicoloured noise inherited from the previous boot's PSRAM contents.

**Root cause:** `ps_malloc()` allocates PSRAM but **does not zero the region**. PSRAM retains its
contents across a software reset. On first `lv_timer_handler()` call, only the regions that LVGL
considers "dirty" are rendered; the rest remain at whatever the PSRAM held.

**Fix:** Call `memset(draw_buf, 0, BUF_PIXELS * sizeof(uint16_t))` immediately after `ps_malloc`.

---

### P6 — COM port held by stale process (PermissionError 13)

**Symptom:** `pio device monitor` (or Upload and Monitor) fails with `serial.serialutil.SerialException:
[Errno 13] could not open port COM5: PermissionError(13, ...)`.

**Root cause:** A previous `pio device monitor` or build/upload process left a `pio.exe` or `python.exe`
instance holding the COM port open. Windows does not allow two processes to open the same serial port.

**Fix:**
```powershell
Get-Process pio, python | Stop-Process -Force
```
Then re-run the monitor. If the port is still held, check Device Manager for COM5 and use
`handle.exe` (Sysinternals) to find the locking process.

---

### P7 — PlatformIO build cache using stale objects after header change

**Symptom:** After editing a shared header (such as `board_pins.h`), PIO compiled without errors but
the firmware on device still behaved as before the change.

**Root cause:** PlatformIO caches compiled `.o` objects. When a header changes, files that include
it transitively may not be detected as stale by PIO's dependency scanner, especially for library
files under `lib/`.

**Fix:** Always run `-t clean` before `-t upload` after changing headers:
```bash
pio run -e guition-jc3248w535 -t clean
pio run -e guition-jc3248w535 -t upload
```

In VS Code: PlatformIO sidebar → *Project Tasks* → *guition-jc3248w535* → *General* → **Clean**, then **Upload**.

---

### P8 — LVGL tick not advancing (animations frozen, no touch response)

**Symptom:** LVGL renders the first frame but UI does not respond to time-based events; buttons
appear but animations stall and touch has no visible effect.

**Root cause:** `LV_TICK_CUSTOM` in `lv_conf.h` is not read by LVGL's own compiled `.c` files when
LVGL is a separate PlatformIO library dependency. LVGL compiles against its bundled `lv_conf_template.h`
which has `LV_TICK_CUSTOM 0`, so the internal tick is never advanced.

**Fix:** Call `lv_tick_inc(millis() - last_ms)` manually in `loop()` before `lv_timer_handler()`.
This works regardless of whether `LV_TICK_CUSTOM` is picked up.

---

### P9 — Partial drawing lands at the top of the panel

**Symptom:** A test pattern drawn with `fillRect()` (seven colour bands down the panel) showed only
the last band, blue, as a bar at the top of the screen. Serial reported success.

**Root cause:** `Arduino_AXS15231B` sends CASET/RASET for every draw, but over QSPI the panel
does not honour the row window for partial writes. Each write starts at the top, so later draws
overwrite earlier ones there. Full-panel writes from (0,0) are unaffected, which is why
`fillScreen()` and the full-frame LVGL flush work.

**Fix:** Never draw straight to the panel with GFX primitives. Draw into a 320×480 RGB565 frame in
PSRAM and push it with a single `draw16bitRGBBitmap(0, 0, frame, 320, 480)` (`display_push_frame()`
in this repo). LVGL must use `LV_DISPLAY_RENDER_MODE_FULL` for the same reason.

## BLE / Nordic UART Service (Bluedroid API)

```cpp
#include <BLEDevice.h>
#include <BLEServer.h>

// core 3.x: getValue() returns Arduino String, not std::string
void onWrite(BLECharacteristic* c) {
    String v = c->getValue();
    // use v.c_str(), v.length()
}
```

## Known Hardware Quirks Summary

| Issue | Root cause | Fix |
|-------|-----------|-----|
| Screen blank / dashed line at boot | Wrong init sequence (default 180×640) | Pass `axs15231b_320480_type1_init_operations` explicitly |
| Hardware rotation (rotation=1) breaks display | AXS15231B MADCTL incomplete on this variant | Keep rotation=0; use software rotation |
| Touch reads all zeros | Unlock command not sent, or repeated-start used | Send 8-byte `{0xb5,0xab,...}` with full STOP before each `requestFrom` |
| Touch INT on wrong GPIO | Wrong pin in `attachInterrupt` | INT is GPIO **3** |
| Multiple touch events per tap | AXS15231B fires 3–6 INT pulses per touch | Debounce with a latch cleared on 80 ms release timeout |
| Stripe artifacts in LVGL rotation | flush_cb using area coords instead of gfx dimensions | Use `gfx->width()` / `gfx->height()` in flush, not area math |
| Only one bar at the top; other drawing missing | Panel ignores the row window for partial writes | Draw into a full PSRAM frame, push it from (0,0) (§P9) |
| Stale PSRAM pixels at boot | `ps_malloc` does not zero memory | `memset(buf, 0, size)` after allocation |
| `ledcSetup` not declared | Removed in Arduino core 3.x | Use `analogWrite()` or new `ledcAttach()` API |
| `std::string` compile error in BLE (Bluedroid only) | Core BLE library API changed in core 3.x | Change `std::string` → `String` in Bluedroid callbacks. Not relevant to NimBLE |
| Flash reports 8192 KB / boot rejects partitions | `esp32-s3-devkitc-1` defaults to 8 MB flash | Add `board_upload.flash_size = 16MB` |
| `LV_COLOR_DEPTH is deprecated` warnings | Renamed in LVGL 9.5+ | Define `LV_COLOR_FORMAT_DEFAULT LV_COLOR_FORMAT_RGB565` instead |
| PSRAM not available / ps_malloc returns null | Missing build flags | Add `-DBOARD_HAS_PSRAM` and `board_build.arduino.memory_type = qio_opi` |
| COM port permission error | Stale pio.exe or python.exe holds port | `Get-Process pio, python \| Stop-Process -Force` |
| Firmware unchanged after header edit | PIO build cache | Run `-t clean` before `-t upload` after any header change |
